# バージョンアップ時のドキュメント整合性監査

`Directory.Build.props` の `<Version>` を上げるたびに、`docs/` と `README.md` の中で
「vX.Y.Zで削除された」のようなバージョン番号付きの記述が古いバージョンのまま残ったり、
`samples/` のコメント・XML docが実際には存在しない(既に削除・改名された)識別子を
参照したまま残ったりする。これは片方だけ直して乖離する典型パターンで、CLAUDE.mdが
明示的に警告している問題そのもの。このスキルはその洗い出しを毎回手作業でやり直さずに
再現するための手順。

## 手順

1. **機械チェックを走らせる**

   ```
   bash .claude/skills/version-bump-doc-audit/audit-version-refs.sh
   ```

   このスクリプトは以下を行う（すべて正規表現ベースのヒューリスティックであり、
   出力は「レビュー候補」であって確定した不具合ではない。偽陽性は許容し、
   偽陰性（見逃し）を避ける方向に寄せてある）:

   - `Directory.Build.props` の `<Version>` と `CHANGELOG.md` 先頭セクションの
     バージョンが一致しているかを確認する
   - `CHANGELOG.md` の現在バージョンのセクションから、「削除した」「Removed」に
     言及している段落中のバッククォート識別子を候補として抽出する
   - `docs/*.md` と `README.md` の中でその識別子に言及している行を探し、
     現在バージョンと異なる `vX.Y.Z` が書かれている行を列挙する
   - `samples/` 配下のコメント・XML doc がその識別子を参照していて、かつ
     `src/` のどこにも実在しない場合（＝サンプルのコメントが削除済みの型名を
     参照したまま残っている）を列挙する

2. **候補を1件ずつ裏取りする**

   スクリプトの出力はノイズを含む。各候補について:

   - `git log --diff-filter=D --summary --all -- '**/<型名>.cs'` で、その型が
     実際にどのコミット（＝どのバージョン）で削除されたかを確認する
   - `CHANGELOG.md` の各バージョンセクションを読み、その識別子が実際に
     どのバージョンの Breaking Changes / Removed に属するかを確認する
   - ドキュメント側の記載バージョンと実際の削除バージョンが食い違っていれば、
     そのドキュメントの記載を修正する（`CHANGELOG.md` 自体は変更点の一次記録なので
     基本的に触らない。触るのは `docs/*.md` / `README.md` / `CLAUDE.md` 側）
   - `samples/` 側のヒットは、コメントが指している型名が実際にそのサンプルで
     使われている型名と一致しているか確認する。ズレていれば
     `samples/CSStack.TADA.Sample/Domain/*Exceptions.cs` 等で実際に定義されている
     型名にコメントを合わせる

3. **`docs/migration.md` の構造を確認する**

   `migration.md` はバージョン間の移行手順を「## vA → vB」の見出しでまとめている。
   新しいバージョンの破壊的変更は、既存の見出しに追記するのではなく、
   **新しい `## v(直前のバージョン) → v(今回のバージョン)` セクションを追加する**。
   過去に一度、複数バージョンにまたがる変更が1つの見出しの下にまとめて書かれてしまい、
   バージョン番号が丸ごとずれていたことがある。見出しを追加・改名したら、
   ファイル冒頭の目次テーブルとファイル内の自己参照アンカー（`[...](#見出しのスラッグ)`）
   も両方直すこと。GitHub の見出しスラッグ規則は「小文字化 → `.`/`:`/`→` 等の記号を除去
   → 空白をハイフンに置換」（日本語はそのまま残る）。

4. **仕上げの確認**

   ```
   dotnet build          # 0 警告 0 エラーを維持
   dotnet format --verify-no-changes
   ```

   `samples/` のコメントを直した場合は、実際に参照している型名が
   コンパイルの通る本物の型名になっているか確認する（ビルドは通っても、
   コメントの中の型名の誤りはコンパイラでは検出できないので目視が必要）。

5. **CHANGELOG.md との対応を確認する**

   `CHANGELOG.md` の各項目末尾には多くの場合「→ docs/xxx.md を参照」という
   ポインタが付いている。今回のバージョンの `### Breaking Changes` / `### Added` /
   `### Documentation` の各項目を上から読み、挙げられている `docs/` ファイルが
   実際にその変更を反映しているか（3の探索で漏れていないか）を最後に目視で確認する。

## このスキルの限界

- 識別子抽出は正規表現ベースなので、`docs/` が「バージョンに一切触れずに」古い型を
  紹介してしまっているケース（バージョン番号自体が無いので比較のしようがない）は
  検出できない。CHANGELOG の該当セクションを実際に読んで判断すること
- 段落単位での抽出のため、無関係な識別子が候補に混ざることがある
  （例: 削除されていない `NestedTransactionException` が、削除された例外クラス群の
  説明と同じ段落に登場するために候補に上がる）。これは意図的なトレードオフ
